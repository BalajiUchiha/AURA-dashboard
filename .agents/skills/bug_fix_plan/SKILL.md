name: bug_fix_plan
description: |
  **What it does:** Turns an existing audit into a concrete implementation plan (or task list) for fixing the bug.
  **When to use:**
  - An audit (`AUDIT.md`) has already been generated by `bug_trace_audit`.
  - The user asks to plan the fix, create an implementation plan, or convert the audit into a step‑by‑step task list.
  - The request mentions “plan the fix”, “create a plan”, “task list”, or similar wording.
---

## Body – Step‑By‑Step Procedure
1. **Locate the most recent matching audit**
   - If the user provides a path, use it; otherwise, scan `audits/` for the latest folder whose name matches the bug slug (or simply the newest timestamp).
   - Verify that an `AUDIT.md` exists inside. If none is found, abort and tell the user to run `bug_trace_audit` first.
2. **Read `AUDIT.md`**
   - Parse the sections: *Bug as understood*, *Root‑cause hypothesis*, *Evidence (file + line references)*, *Full trace*, and *Confidence level*.
   - Extract each concrete finding that ties a file/line to the bug.
3. **Scope the plan strictly to the bug fix**
   - Only create steps that address a finding from the audit. Every step must reference the exact audit finding it resolves (e.g., `File: src/.../catalogue.repository.ts, line 42 – missing error check`).
   - Do **not** add unrelated refactors, renames, formatting clean‑ups, or “while I’m here” changes.
4. **Validate each proposed change**
   - Ensure none of the steps would: 
     - Add a default/fallback value for a possibly missing field.
     - Loosen validation merely to make a request succeed.
     - Catch an error without propagating a failure response.
     - Silently convert a should‑fail case into success.
   - If the user’s requested fix would require any of those patterns, stop and flag the issue back to the user instead of planning it.
5. **Write `PLAN.md`**
   - Place it in the same audit folder.
   - List steps **in exact execution order**:
     1. **File change** – path, function/class, line range, and a concise description of the modification.
     2. **Database/schema migration** – if applicable, include migration name and SQL snippet.
     3. **Rollback note** – how to revert this change safely.
   - After the change list, add a **Verification section** that specifies:
     - Which request(s) to exercise (HTTP method + endpoint).
     - Expected success response body (e.g., `{"success":true,...}`) vs failure response.
     - The resulting DB state that should exist after a successful fix.
   - End the document with a status line `Status: PENDING APPROVAL`.
6. **Never execute any code** – this skill only creates the `PLAN.md` file.
7. **Hand off** – output a single line to standard output indicating the full path of the created `PLAN.md` so downstream skills can locate it.
